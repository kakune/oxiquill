title: プロジェクト設定
description: Astro、Starlight、Oxiquill path、生成物を一つの project state として設定します。
---

Oxiquill は一つの project config を読み込み、development、check、generation、build、test、clean のすべてで同じ resolved path を使います。すべての command に同じ `--config` を渡す場合を除き、`astro.config.mjs` は project root に置きます。

## 最小構成

```js
import starlight from '@astrojs/starlight';
import { defineOxiquillConfig } from 'oxiquill/astro';

export default defineOxiquillConfig({
  framework: { starlight },
  site: 'https://example.com',
  title: 'My Docs',
  sidebar: [{ label: 'Overview', items: [{ label: 'Home', slug: 'index' }] }]
});
```

```ts
// content.config.ts
import { defineCollection } from 'astro:content';
import { docsLoader } from '@astrojs/starlight/loaders';
import { docsSchema } from '@astrojs/starlight/schema';
import { createOxiquillCollections } from 'oxiquill/content';

export const collections = createOxiquillCollections({ defineCollection, docsLoader, docsSchema });
```

`defineOxiquillConfig()` は static output、Oxiquill の Markdown transform、Preact、Starlight を設定済みの Astro config を返します。

## 設定 field

| Field                             | 意味                                                                                                                                                                |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`, `description`, `sidebar` | 対応する Starlight setting の shorthand。                                                                                                                           |
| `desktopTableOfContentsToggle`    | 永続化される desktop 目次 control を有効にします。default は `true` です。                                                                                          |
| `starlight`                       | その他の Starlight option。同じ setting はこちらが shorthand より優先されます。                                                                                     |
| `framework.starlight`             | `@astrojs/starlight` から import する必須の Starlight integration factory。                                                                                         |
| `framework.preact`                | 組み込み用途向けの optional Preact integration-factory override。                                                                                                   |
| `integrations`                    | Oxiquill、Preact、Starlight の後に追加する Astro integration。                                                                                                      |
| `markdown`                        | 対応する Astro Markdown setting/plugin。Oxiquill 必須 plugin が先に動きます。                                                                                       |
| `vite`                            | 追加の Vite setting。必須 alias、dedupe、worker plugin、filesystem access は保持されます。                                                                          |
| `paths`                           | 下記の source/cache/generated/public path。                                                                                                                         |
| `python`                          | Pyodide download の `preload`、`offline` と optional `packageMirror`。                                                                                              |
| `rust`                            | Rust モジュールのグループ化。`page`（既定値）、`directory`、`site`、またはキーを返す関数。                                                                          |
| `missingTranslations`             | `fallback`（既定値）は Starlight のフォールバックページを維持し、`omit` は翻訳したページだけを生成・リンクします。[多言語サイト](#多言語サイト)を参照してください。 |
| `docRedirects`                    | 転送先を `base` からの相対パスの文書ページで指定するリダイレクト。[文書のリダイレクト](#文書のリダイレクト)を参照してください。                                     |
| その他の Astro field              | Astro に渡されます。Oxiquill の output は常に static です。                                                                                                         |

Astro config を手動で組み立てる場合だけ `oxiquillIntegration()` を使います。受け取る option は `base`、`markdown`、`paths`、`python`、`rust`、`vite` で、Preact と Starlight は caller が追加します。`missingTranslations` と `docRedirects` は Starlight と Astro の設定も変更するため、`defineOxiquillConfig()` だけが受け取ります。

interactive cell、Mermaid、KaTeX、public-asset base path には Oxiquill の unified pipeline が必要なため、`markdown.processor` は Oxiquill が管理します。custom processor は未対応で `TypeError` になり、代わりに対応する Markdown field と追加の `remarkPlugins` / `rehypePlugins` を設定します。

## Desktop の目次

目次があるページでは、Starlight の mobile disclosure を保ったまま、Oxiquill が desktop 用の折りたたみ・展開 button を追加します。目次を折りたたむと右列全体がなくなり、main content が空いた幅を使います。設定は現在の browser tab の `sessionStorage` に `oxiquill-table-of-contents-collapsed` key で保存され、左 sidebar の設定とは独立しています。

Starlight の常時表示 desktop 目次を維持するには `desktopTableOfContentsToggle: false` を設定します。

```js
export default defineOxiquillConfig({
  desktopTableOfContentsToggle: false,
  framework: { starlight },
  title: 'My Docs'
});
```

`tableOfContents: false` のページと splash page には control を出力しません。`starlight.components` に consumer が指定した entry は Oxiquill の default より優先され、`PageFrame`、`TableOfContents`、`TwoColumnContent` の override も保持されます。

目次の列幅は `--oq-toc-width` です。既定値の `clamp(14rem, 18vw, var(--sl-sidebar-width))` は、小さなデスクトップ画面では列を狭めて本文の幅を確保し、大きな画面ではサイドバーと同じ幅になります。さらに広い画面では、残りの幅を本文と目次に分けて両方を中央付近に保ちます。長い項目は列の中で折り返し、開閉ボタンはどの幅でも列の境界に表示されます。固定幅にするには `:root` に指定します。

```css
:root {
  --oq-toc-width: 16rem;
}
```

このプロパティはOxiquillの開閉レイアウトに適用されます。`desktopTableOfContentsToggle: false` では、Starlight自体の列幅の計算を使います。

## 本文の幅

左のサイドバーを折りたたむと現在の `--sl-content-width` に `--sl-sidebar-width` が加わり、目次を折りたたむと目次の列幅 `--oq-toc-width` が加わります。両方を展開したときの既定の本文幅は変わりません。

本文幅と列幅を変更するには、`starlight: { customCss: ['./styles/custom.css'] }` のように `starlight.customCss` にスタイルシートを登録します。このCSSはOxiquillのCSSの後に読み込まれます。両方のプロパティを `:root` に指定してください。

```css
:root {
  --sl-content-width: 80rem;
  --sl-sidebar-width: 20rem;
}
```

`--sl-content-width: 100%` のような可変幅は、どの折りたたみ状態でも可変幅のままです。Starlightは、スプラッシュページを含むサイドバーのないページに別の基準幅を指定します。必要に応じて `:root:not([data-has-sidebar]) { --sl-content-width: 100%; }` で上書きしてください。

サイト全体を変えずに、特定のページだけ本文幅の制限を外せます。frontmatter に `contentWidth: full` を指定すると、本文が左右のナビゲーション列の間をすべて使い、どちらの開閉ボタンもそのまま使えます。列の多いリファレンス表や複数のグラフを載せるページに向いています。文章中心のページは既定の幅のままにしてください。

```mdx
---
title: API Index
contentWidth: full
---
```

`createOxiquillCollections()` は docs schema に `contentWidth`（`default` または `full`）を追加します。独自の docs schema を使うプロジェクトでは、同じ省略可能な field を追加してください。

独自の `PageFrame` を使っても、Oxiquillの `TwoColumnContent` による目次の折りたたみ時の拡幅は有効です。サイドバーの折りたたみ時の拡幅にはOxiquillの `PageFrame` が必要です。

## 多言語サイト

Starlightは、翻訳のないページを既定の言語の内容で補います。このフォールバックページにより、どの言語にもすべてのルートが存在します。翻訳したページだけを各言語に含めるには `missingTranslations: 'omit'` を指定します。

```js
export default defineOxiquillConfig({
  framework: { starlight },
  missingTranslations: 'omit',
  starlight: {
    defaultLocale: 'root',
    locales: {
      root: { label: 'English', lang: 'en' },
      ja: { label: '日本語', lang: 'ja' }
    }
  }
});
```

OxiquillはAstroがページを生成する前にフォールバックのルートを取り除きます。そのため、これらのルートはHTML、サイトマップの項目、検索データのいずれも生成せず、開発サーバーでは404を返します。ナビゲーションも生成したページに合わせます。

- 言語選択には、現在のページがある言語だけを表示します。ほかの言語にページがない場合は表示しません。
- サイドバーから、翻訳のないページへのリンクと、それによって空になったグループを除きます。
- 前後のページへのリンクは翻訳のないページを飛ばします。frontmatter の `prev` と `next` も引き続き適用します。
- `hreflang` の代替リンクとサイト名のリンクは、生成したページだけを指します。

既定値の `'fallback'` はStarlightの動作を維持します。`'omit'` にはプリレンダリングするStarlightページが必要です（既定の設定）。このモードはOxiquillの `LanguageSelect` コンポーネントとルートミドルウェアを追加します。`starlight.components` の `LanguageSelect` が優先され、`starlight.routeMiddleware` の項目はOxiquillの後に実行されて、絞り込んだナビゲーションを受け取ります。

## 文書のリダイレクト

Astroは `redirects` の転送元を `base` の下で照合しますが、対応するルートが見つからない転送先には `base` を付けません。Starlightが表示するページはこの転送先に当たります。移動した文書ページには `docRedirects` を使ってください。転送先には `base` からの相対パスで文書ページを指定し、Oxiquillが `base` を付けます。

```js
export default defineOxiquillConfig({
  base: '/docs/',
  docRedirects: {
    '/guides/setup/': '/guides/getting-started/',
    '/ja/old-guide/': { status: 301, destination: '/ja/guide/' }
  },
  framework: { starlight }
});
```

この例では `/docs/guides/setup/` が `/docs/guides/getting-started/` に転送されます。転送先は一つの `/` で始め、ルートのパラメーターを含めることはできません。転送先のページが生成されない場合、たとえば入力ミスや、`missingTranslations: 'omit'` で翻訳のない転送先を指定した場合は、ビルドが失敗します。外部サイトや文書以外の転送先はAstroの `redirects` に指定してください。同じ転送元を両方に指定することはできません。

## 日本語の組版

`oxiquill/styles/japanese.css` は、言語が日本語（`lang="ja"` または `ja-` で始まるタグ）のコンテンツに組版の設定を適用します。厳格な禁則処理により小書きの仮名や長音符を行頭に置かず、本文と見出しの行間と字間を調整します。日本語のルートで表示される未翻訳のフォールバックページを含め、ほかの言語のコンテンツには影響しません。`starlight.customCss` に追加してください。

```js
starlight: {
  customCss: ['oxiquill/styles/japanese.css', './styles/custom.css'];
}
```

値を調整するには、このファイルの後に読み込むスタイルシートで `:root` に次のプロパティを指定します。

| プロパティ                       | 既定値   | 対象                                                         |
| -------------------------------- | -------- | ------------------------------------------------------------ |
| `--oq-ja-line-height`            | `1.9`    | 段落、リスト項目、定義、引用、表のセル、キャプション         |
| `--oq-ja-letter-spacing`         | `normal` | 上と同じ本文の要素                                           |
| `--oq-ja-heading-line-height`    | `1.4`    | ページタイトルと見出し                                       |
| `--oq-ja-heading-letter-spacing` | `0.01em` | ページタイトルと見出し                                       |
| `--oq-ja-word-break`             | `normal` | 本文。`auto-phrase` は対応ブラウザーで文節の区切りで改行する |

## Path field

| Field                  | Default                         | 解決基準                    |
| ---------------------- | ------------------------------- | --------------------------- |
| `workspaceRoot`        | project root                    | current project/config root |
| `frameworkRoot`        | install 済み `oxiquill` package | absolute/package location   |
| `docsDir`              | `content/docs`                  | `workspaceRoot`             |
| `cratesDir`            | `crates`                        | `workspaceRoot`             |
| `publicDir`            | `public`                        | `workspaceRoot`             |
| `cacheDir`             | `.oxiquill`                     | `workspaceRoot`             |
| `downloadCacheDir`     | `.cache/oxiquill/downloads/v1`  | `workspaceRoot`             |
| `generatedDir`         | `generated`                     | `cacheDir`                  |
| `rustCellsDir`         | `rust-cells`                    | `cacheDir`                  |
| `haskellCellsDir`      | `haskell-cells`                 | `cacheDir`                  |
| `publicAssetsDir`      | `oxiquill`                      | `publicDir`                 |
| `rustWasmPublicDir`    | `rust-wasm`                     | `publicAssetsDir`           |
| `haskellWasmPublicDir` | `haskell-wasm`                  | `publicAssetsDir`           |
| `pyodidePublicDir`     | `pyodide`                       | `publicAssetsDir`           |
| `licensesPublicDir`    | `licenses`                      | `publicAssetsDir`           |

各 path は relative string、absolute string、`file:` URL を受け取ります。nested relative path は偶然の working directory ではなく、表に示した parent から解決されます。

Astro の `root`、`publicDir`、`outDir`、`cacheDir` と Oxiquill の path setting が同じ directory を示す場合、正規化後の location が一致しなければなりません。明示値の競合は error になり、Oxiquill が黙って一方を選ぶことはありません。すべての CLI command は file の読み書きや clean より前にこの config を解決します。

## 生成される Rust アセット

実行可能な `.oxiquill/generated/cells.json` には、バージョン 1 の `rust` レジストリが含まれます。各 Rust セルは必ず 1 つのモジュールに属し、各モジュールは `page-3f2a9c41d07b5e68` のような `<mode>-<hash>` という名前の [Rust モジュールのグループ](#rust-モジュールのグループ化) に対応します。

各モジュールには、ビルドのフィンガープリント、JavaScript グルーと Wasm の URL、Wasm の SHA-384 整合性情報、バイト数、セル ID が記録されます。`public/oxiquill/rust-wasm/` のファイル名は `page-3f2a9c41d07b5e68-<hash>.js` や `page-3f2a9c41d07b5e68-<hash>.wasm` の形式です。内容に基づく URL は不変です。レジストリは `publicDir` からの相対パスを保存し、Astro はカスタムのランタイムディレクトリも含めて、設定された `base` に合わせてブラウザー用 URL を解決します。

Rust ワーカーは、そのモジュールのセルが初めて実行されたときにアセットを読み込み、取得時に Wasm の整合性を検証します。テキストのみ、または Python のみのページは Rust モジュールのアセットを取得しません。開発中の更新ではフィンガープリントが変わったモジュールだけを無効化します。キャンセルとタイムアウトは引き続き Rust ワーカー全体をリセットします。古い登録済みアセットは、新しいレジストリの公開後に削除されます。

ソースのみを生成する `docgen` は Rust をコンパイルしません。実行可能なアセットを生成するには、`oxiquill docgen --wasm dev` またはサイトのビルドを実行してください。生成されたマニフェストやアセットを直接編集しないでください。

## Python download

```js
export default defineOxiquillConfig({
  python: {
    preload: false,
    offline: process.env.OXIQUILL_OFFLINE === '1',
    packageMirror: new URL('https://packages.example/pyodide/')
  },
  paths: {
    downloadCacheDir: new URL('./.cache/verified-downloads/', import.meta.url)
  }
});
```

`python.offline` の default は `false` です。`python.packageMirror` は string または URL を受け取り、lockfile の integrity check を変えずに package download base だけを変更します。`paths.downloadCacheDir` も string または URL を受け取ります。公開 type の `OxiquillPythonOptions` と `OxiquillPathOptions` がこれらの field を定義します。

## 優先順位と merge

1. `--config <path>` が config file を選び、省略時は Astro 標準の探索を使います。
2. 明示した project setting が default より優先されます。
3. `starlight.title`、`starlight.description`、`starlight.sidebar` が shorthand field より優先されます。
4. Consumer の Markdown、Vite、CSS、component、integration の追加は Oxiquill 必須 entry の後に保持されます。
5. path の競合、Oxiquill integration の欠落・重複、config 読み込み失敗は generation/clean より前に失敗します。

## Clean の ownership と安全性

`oxiquill clean` が再帰削除する resolved root は `cacheDir`、Astro の `outDir`、`publicAssetsDir` の3つだけです。`downloadCacheDir` は削除しません。default の verified download cache `.cache/oxiquill/downloads/v1` は clean 後も残り、次の generation で再利用できます。

default の `.oxiquill`、`dist`、`public/oxiquill` は生成専用 location として予約され、ownership marker がなくても clean できます。custom cleanup root では、対応する generation/build lifecycle が存在しないか空の directory を claim し、`.oxiquill-ownership.json` を書きます。matching marker のない既存の non-empty custom directory を生成物とは推測しません。marker を手動で作成・編集しないでください。

再帰削除する root はすべて `workspaceRoot` 内になければなりません。cleanup root 同士は disjoint であり、`docsDir`、`cratesDir`、`publicDir`、`frameworkRoot`、選択した Astro config、認識済み project config/manifest/lock file、persistent download cache、`.git` や `node_modules` など検出した VCS/package-installation state とも重複できません。generated child role 同士の重複も拒否します。authored/generated の包含で許可する唯一の例外は、`publicAssetsDir` が `publicDir` の厳密な子である関係です。`publicDir` と同一にはできず、別の authored public subtree の内側にも置けません。

Oxiquill は比較・削除前に既存 path と symlink ancestor を canonicalize します。clean は最初の再帰削除より前に全 root と全 ownership marker を検証します。unsafe/unowned root が一つでもあれば何も削除せず、diagnostic に field、absolute resolved path、conflicting path role、corrective action を示します。

## Runtime fingerprint

runtime fingerprint には machine-local path ではなく semantic build input が入ります。Python fingerprint は Pyodide version、lockfile SHA-256、検証済み core-file hash、選択 package metadata、requested package set を含みます。Haskell build fingerprint は cell、generated source、supported compiler-version prefix、compiler が報告した正確な version（または unavailable state）を含みます。Haskell compiler command、executable path、diagnostic text は除外されるため、同等 toolchain の移動だけでは rebuild せず、reported version や supported-version policy の変更では rebuild します。

Rust と Haskell の build fingerprint は、installed generator の content hash と package identity も含みます。workspace package version が変わらなくても、codegen、build flag、postprocessing、staging、runtime data の変更を検出します。Rust はさらに `RUSTFLAGS`、`CARGO_ENCODED_RUSTFLAGS`、すべての `CARGO_PROFILE_*`、`CARGO_BUILD_*`、`CARGO_TARGET_*`、`BINARYEN_*` 環境変数と、workspace root の `.cargo/config`、`.cargo/config.toml` を hash 化します。並列数だけを決める `CARGO_BUILD_JOBS` と `BINARYEN_CORES`、および無関係な環境変数は除外します。各モジュールは、解決済みの依存関係と workspace のビルドに参加する helper の manifest も fingerprint に含めます。artifact mode も記録し、production output は dev request に再利用できますが、dev output は production 用に rebuild します。

published Rust、Haskell、Python file を再利用する前に、記録した byte size と SHA-256 digest を検証します。開発時は、内容に基づく名前の Rust モジュール file と生成したモジュールの source を存在と size で確認するため、変更のない sync はモジュールの bytes を読みません。production build は常に SHA-256 を検証します。file の欠落、編集、切り詰めは regeneration の対象です。integrity record のない古い runtime state も自動的に再生成します。

## Compiler Cache

compiler cache は設定した `cacheDir` 内の `build-cache/rust-target`（Cargo）と `build-cache/haskell/<mode>-<ghc-version>`（Haskell）に置きます。runtime staging や compile failure 後も保持します。Haskell は安定した cached source path と未変更 source の timestamp を使い、GHC の module object 再利用を可能にします。mode と正確な compiler version ごとに cache を分離し、Cargo の dependency recompilation 判定は Cargo に任せます。

Release Rust build は `wasm-opt -O` の結果を `build-cache/wasm-opt` に cache します。optimizer は `PATH` 上の `wasm-opt`、または検証済みの Binaryen 117 です。key は input の bytes と size、optimizer の version と executable hash、最適化引数、schema version、`BINARYEN_CORES` を除くソートした `BINARYEN_*` 環境変数です。optimizer の変更は Rust build の再利用を無効にします。dev build は最適化を行いません。cache hit 時は content integrity を検証し、bytes を build stage にコピーします。破損した entry は自動再生成します。直近に使用した少なくとも 16 件、大きなサイトでは Rust モジュール数の 2 倍の結果を保持し、通常は build failure 後も残ります。`oxiquill clean` または `pnpm build:clean` で削除でき、verified download は保持します。

Cargo target directory はすべての Cargo 実行に渡します。明示した `CARGO_TARGET_DIR` が優先され、user-owned の外部 target directory は clean で削除しません。compiler cache は published output、verified download cache と別に管理します。`oxiquill clean` は Oxiquill-owned compiler cache を削除し、verified download は保持します。

ancestor の `.cargo` file、`$CARGO_HOME/config*`、config が参照する file など workspace root 外の設定は fingerprint に含みません。これらを変更した後は、repository では `pnpm build:clean`、consumer project では `oxiquill clean` の後に `oxiquill build` を実行してください。

## Base path と public asset

subpath 配下へ公開するときは Astro の `base` を設定します。Oxiquill は interactive-cell manifest、language runtime、diagram、`/media/...` reference に適用します。`base` 自体が `/media` または同じ prefix で始まる場合も、authoring ではすべての public URL を root-relative の `/media/...` 形式で記述します。configured base は手動で追加せず、通常の Markdown pass に authored URL を prefix させます。文書ページへのリダイレクトには、同じく base を付ける [`docRedirects`](#文書のリダイレクト) を使います。

生成 runtime は `.oxiquill` と `public/oxiquill`、verified download cache は `.cache/oxiquill/downloads/v1`、最終 static site は Astro の `outDir`（通常 `dist`）に置かれます。生成 directory と ownership marker を直接編集しないでください。download cache は build や output 再生成をまたいで保持できますが、file は利用前に毎回検証されます。

生成 directory を変更するときは、resolved cache、helper-crate target、output、public-asset path に合わせて `tsconfig.json` の exclusion も更新します。そうしないと `**/*` のような広い include により、Astro/TypeScript が Pyodide などの生成 JavaScript を output ではなく source として解析することがあります。

`python.preload` の default は `false` です。有効にすると Python cell がある page の DOM ready 時に準備を始めます。詳細は [Python runtime asset](/ja/guides/python-runtime/#browser-の準備) を参照してください。

`python.additionalPackages` はパッケージ名から `{ version, license, licenseFiles }` への mapping です。固定 Pyodide lock の配布物を許可リストへ追加します。`python.experimentalSetup` は既定で `false` で、有効にすると同じページの Python setup を毎回再実行できます。詳細は [Python runtime asset](/ja/guides/python-runtime/) を参照してください。

## Rust モジュールのグループ化

`rust.grouping` は、どのページが同じ Rust モジュールを共有するかを決めます。どの方式でも処理は同じで、`paths.rustCellsDir` 以下の 1 つの Cargo workspace に、グループごとのメンバー crate と、内容に基づく名前の Wasm モジュールを 1 つずつ生成します。Rust セルのないページにはモジュールを生成しません。1 つのページが複数のモジュールにまたがることはないため、ページ内の `definitions`、`uses`、`exports`、`dependsOn` は常に 1 つの crate に収まります。

| 値                     | グループのキー          | 適した場面                                                                                                                     |
| ---------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `'page'`（既定値）     | ページのパス            | ほとんどのサイトと大きな book。編集時は 1 ページ分だけを再ビルドし、読者は使うページのモジュールだけを取得します。             |
| `'directory'`          | ページの親ディレクトリ  | 章を順に読み進め、章内のページが helper を共有する場合。少数の大きなモジュールでモジュールごとの負担を抑えます。               |
| `'site'`               | サイト全体で 1 つのキー | まとめて読まれる小さなページが多い場合。モジュールは 1 回の取得でキャッシュされますが、Rust の編集ごとに全体を再ビルドします。 |
| `({ path }) => string` | 返された文字列          | book の部ごとに 1 モジュールにするなど、その他の分け方。                                                                       |

パスは `paths.docsDir` からの POSIX 相対パスで、ロケールの接頭辞も含みます。そのため `guides/a.mdx` と `ja/guides/a.mdx` が同じ `directory` グループになることはありません。キーは Unicode NFC に正規化されるため、分解形のファイル名を保存するファイルシステムでも同じモジュールになります。関数は副作用のない純粋関数にしてください。凍結された `{ path }` を受け取り、生成ごとに Rust セルのある各ページで 1 回呼ばれ、256 文字以下の空でない正しい文字列を同期的に返す必要があります。それ以外の結果はページ名を示して生成を失敗させます。関数はプロジェクト設定に書くため、CLI、Astro、開発ランタイムで同じように使われ、設定ファイルを保存すると開発ランタイムがグループを作り直します。

```js
export default defineOxiquillConfig({
  framework: { starlight },
  title: 'My Book',
  // `part-1/...` や `ja/part-1/...` など、最上位の部ごとに 1 モジュール。
  rust: {
    grouping: ({ path }) =>
      path
        .split('/')
        .slice(0, path.startsWith('ja/') ? 2 : 1)
        .join('/')
  }
});
```

モジュール ID は方式名とキーの 16 文字のダイジェストを組み合わせたものです（`page-…`、`directory-…`、`site-…`、`custom-…`）。大文字小文字を区別しないファイルシステムでも小文字のまま扱え、Windows でも Cargo の出力パスを短く保ちます。`rust.grouping` を変更したときも、ID、ページ、ソースが変わらないモジュールは再利用します。

ビルドでは、ソース、helper の依存入力、解決済みの依存関係、ツールチェーン、ビルド設定のいずれかが変わったモジュールだけをコンパイルします。古くなったモジュールは 1 回の Cargo 実行でまとめてコンパイルし、依存は `build-cache/rust-target` で共有します。各モジュールのコンパイルが終わり次第、wasm-bindgen と（本番ビルドでは）wasm-opt を上限付きの並列数で実行します。並列数は正の `CARGO_BUILD_JOBS`、指定がなければ利用可能な CPU 数です。`BINARYEN_CORES` を指定しない場合、wasm-opt は同時に最適化するモジュールで CPU を分け合います。出力は実行順に依存せず、クリーンビルドの結果は並列数にかかわらずバイト単位で同一です。`oxiquill build --explain` で計画を確認できます。

読者は実行するセルが必要とするモジュールだけを取得します。共通の依存は一度だけコンパイルされますが、それを使う各モジュールにリンクされるため、合計の転送量と保存容量はモジュール数とともに増えます。

本番ビルドは、いずれかのモジュールが失敗すると何も公開せずに失敗します。`oxiquill dev` のランタイムはビルドできたモジュールをすべて公開します。失敗したモジュールは最後に動作したビルドを維持し、そのページは以前の Rust セルを使いながらコンパイルエラーを表示します。入力が変わるまで再コンパイルはしません。`oxiquill docgen --wasm dev` などの単発コマンドは、代わりに何も公開せず失敗します。

Rust の生成には Cargo と `wasm32-unknown-unknown` ターゲットが必要です。Oxiquill は固定されたランタイム crate と一致する `wasm-bindgen` CLI を `PATH` から使い、なければ公式のホスト向け配布物をダウンロードして固定 SHA-256 を検証し、`paths.downloadCacheDir` に保存します。バージョンの異なる `PATH` 上のバイナリは使いません。本番の最適化も同様に、`PATH` 上の `wasm-opt` または検証済みの Binaryen 117 を `-O` で使います。展開には `tar` が必要です。検証の失敗や未対応のホストでは、期待するバージョンとキャッシュのパスを表示します。一致するツールを `PATH` にインストールしても構いません。

生成される workspace の lock は、ランタイムの完全固定バージョンと、helper workspace が lock している通常依存およびビルド依存のバージョンを出発点にします。helper の dev-dependencies は無視します。Cargo は workspace の依存関係が変わったとき（helper の通常依存やビルド依存の編集を含む）に一度だけこれを解決し、ローカルにキャッシュされていないパッケージがある場合だけネットワークを使います。以降のビルドはすべて `--locked` で実行します。解決に失敗した場合は[トラブルシューティング](/ja/guides/troubleshooting/)を参照してください。

生成されるモジュール crate のソースは `paths.rustCellsDir/modules` 以下の安定したパスに置かれます。ページの削除やグループ変更で不要になったモジュールのソースとアセットは公開後に削除し、以前の単一 crate やページ単位のレイアウトの出力も、`oxiquill clean` なしで次回の生成時に置き換えます。`oxiquill clean` は生成物とコンパイラキャッシュを削除しますが、検証済みのダウンロードは保持します。
